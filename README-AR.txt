تغييرات أمان YAWMAK فقط — بدون أي تعديل على التصميم أو الواجهات

الملفات:
1) src/app/api/admin/route.ts
   - تشديد تغيير صلاحيات المستخدمين: المالك لا يمكن تعديل دوره، ولا يمكن للمسؤول تغيير دوره بنفسه.
   - إبطال جلسات المستخدم بعد تغيير دوره حتى يعاد تحميل صلاحياته من قاعدة البيانات عند تسجيل الدخول.
   - مراجعة الاشتراك أصبحت داخل معاملة قاعدة بيانات واحدة، مع قفل سجل الاشتراك والدفع، والتحقق من أن الطلب والدفع ما زالا قيد المراجعة.
   - لا يقبل قرار مراجعة غير approve أو reject.
   - التحقق من رمز الباقة والسعر قبل تحديث الأسعار.

2) src/app/api/memberships/route.ts
   - إلغاء الاشتراك يحدث داخل معاملة واحدة ويعيد الحساب إلى FREE، ويلغي الطلبات المعلقة والاشتراكات النشطة فقط.
   - طلب الاشتراك لا يفعّل المزايا بنفسه؛ يظل pending_review حتى يعتمد الدفع من الإدارة.

3) supabase/migrations/003_admin_membership_security.sql
   - قيود قاعدة بيانات على الأدوار والباقات وحالات الاشتراك والدفع والمبالغ وفترة الاشتراك.
   - فهارس لتسريع عمليات مراجعة الاشتراكات والمدفوعات.

طريقة التطبيق:
- ارفع الملفات الثلاثة إلى نفس المسارات في مشروع YAWMAK واستبدل النسخ القديمة.
- افتح SQL Editor في قاعدة PostgreSQL/Supabase التي يستخدمها المشروع عبر DATABASE_URL.
- نفّذ محتوى ملف 003_admin_membership_security.sql مرة واحدة.
- بعدها اعمل Commit و Push إلى GitHub وانتظر نشر Vercel.

مهم للأمان:
- DATABASE_URL لازم يظل Environment Variable على Vercel فقط، ولا يوضع في NEXT_PUBLIC_* ولا داخل ملفات المشروع أو GitHub.
- لا تمنح المتصفح اتصالًا مباشرًا بقاعدة البيانات. كل عمليات تغيير role أو membershipPlan يجب أن تمر عبر API الخادمي المحمي بالجلسة والصلاحية.
- لا يوجد نظام مضمون ضد كل الاختراقات؛ هذه التغييرات تقفل مسارات تصعيد صلاحيات ومراجعة اشتراكات غير سليمة، لكنها لا تغني عن حماية حساب Vercel وقاعدة البيانات ومراجعة إعدادات الاستضافة.
- ملف SQL يضيف قيودًا؛ إذا كانت هناك بيانات قديمة مخالفة للقيم المسموحة فسيرفض PostgreSQL تنفيذ الترحيل ويجب مراجعة تلك البيانات قبل إعادة المحاولة.

لم يتم تغيير أي CSS أو مكونات واجهة أو تصميم.
